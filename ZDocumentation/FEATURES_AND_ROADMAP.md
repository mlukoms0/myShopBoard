# FEATURES AND ROADMAP

This document is the working map of *what* myShopBoard builds and *when* — read it before adding a
feature or arguing about priority.

It is derived from a teardown of what the industry-leading products actually ship, split into
**table stakes** (if you don't have it, you don't have a product), **differentiators** (what
separates good from adequate), and **advanced** (later, or never).

---

## 1. The competitive landscape

There are two distinct markets here, and myShopBoard sits in the overlap.

### Market A — Fleet maintenance software (asset-owner side)

Built for the company that *owns* the trucks. Priced **per vehicle**, unlimited users.

| Product | Positioning | Published pricing |
|---|---|---|
| **Fleetio** | The category default for 20–100 unit mixed fleets. **Our primary reference implementation.** | $4 / $7 / $10 per vehicle/mo (Essential / Professional / Premium, annual). Essential and Professional cap at 100 vehicles. |
| **Whip Around** | Inspection-first (DVIR), maintenance bolted on | per vehicle, unlimited users on Standard+ |
| **Samsara / Motive** | Telematics-native; maintenance is a module on top of hardware | bundled with ELD hardware |
| **AUTOsist / Simply Fleet** | Budget SMB tier | per vehicle |
| **UpKeep / Limble / Fiix** | General CMMS, not trucking-specific | **per seat** — $24–55/user/mo |

> **A settled design question:** the fleet-native vendors all charge per *vehicle* with unlimited
> users; the general CMMS vendors charge per *seat*. For an in-house build this means: **never gate
> anything on seat count.** Every mechanic, driver and dispatcher gets their own login. UpKeep's own
> concession — unlimited free view-only users — proves the seat model is wrong for this domain.

### Market B — Heavy-duty repair shop management (shop side)

Built for the shop doing the work. This is where the "shop board" concept comes from.

| Product | Positioning | Published pricing |
|---|---|---|
| **Fullbay** | The heavy-duty independent shop leader | $188 / $258 / $318 per mo per full user; **"Timesheet users" $25/mo** |
| **Tekmetric / Shop-Ware** | Modern auto/light-truck shop management. Best-in-class job boards. | per shop/user |
| **Trimble TMT / Dossier / RTA / Cetaris** | Enterprise private-fleet maintenance | enterprise quote |
| **Decisiv SRM** | The vendor↔fleet communication layer | enterprise |
| **Karmak Fusion / Mitchell 1** | Dealer DMS | enterprise |

> **Fullbay's $25 "Timesheet user" tier is the most instructive price point in the research.** The
> market has already discovered that most shop-floor humans need only *clock on + add notes*, not
> the full application. Our role design should reflect that from day one.

## 2. Feature inventory

### 2.1 The unit page (what the QR sticker opens)

| Tier | Feature | Note |
|---|---|---|
| ✅ Table stakes | Asset record as the hub object — every other record links back to it | Universal across all 10+ products |
| ✅ Table stakes | Spec block: unit number, VIN, year/make/model, plate, group, status, primary meter, secondary meter, assigned operator, photo | The market-standardised field set |
| ✅ Table stakes | Service history list | |
| ✅ Table stakes | Open issues panel | |
| ✅ Table stakes | Service-due meters (OK / Due Soon / Overdue) | |
| ⭐ Differentiator | **Spec + warranty/recall status ordered ABOVE history** | Decisiv's ordering. The tech needs to know "can this go on warranty" *before* starting |
| ⭐ Differentiator | Documents and photos attached to the asset and to each service record | Every vendor meters storage (Fleetio: 2.5 GB → 25 GB), which tells you it's heavily used |
| ⭐ Differentiator | **Prev/next navigation between units** from inside a unit page | Sounds trivial. It is a literal named complaint in Fleetio's Capterra reviews. Five lines of code; mechanics walking a row of trucks will notice |
| 🔵 Advanced | Deferred/recommended work queue that resurfaces next visit | Fullbay "pending repairs", RTA "Planned Work Maintenance" |

### 2.2 QR scanning

| Tier | Feature | Note |
|---|---|---|
| ⭐ Differentiator | QR label → asset resolution, with **printable label sheets generated by the app** | Only Fleetio and Limble do this properly. Mechanics will not hand-make stickers |
| 🎯 **Our edge** | **Scan with the native phone camera — no app install** | **The biggest exploitable gap in the market.** Fleetio requires opening the Fleetio Go app and tapping "Scan Barcode" first; only their *tool* codes work from the native camera. A plain HTTPS URL that deep-links to the unit page beats every incumbent on the single interaction mechanics do 20× a day |
| ✅ Table stakes | Permission check on scan — only open the unit if the user may view it | Fleetio does exactly this |
| 🔵 Advanced | Offline mode for the mechanic view | Gated to UpKeep Professional and Limble Premium+. Shop bays are RF dead zones |

### 2.3 Preventive maintenance

| Tier | Feature | Note |
|---|---|---|
| ✅ Table stakes | PM schedule with **independent thresholds on time AND primary meter AND secondary meter**, whichever comes first | Non-negotiable for a mixed fleet — dump trucks run on engine hours, tractors on miles |
| ✅ Table stakes | Three-state reminder: OK / Due Soon / Overdue, thresholds configurable **per axis** | |
| ✅ Table stakes | **Service Programs** — one maintenance profile applied across many units | With 20–100 units in ~6 configurations, per-vehicle setup is unusable. Build the template *before* per-unit overrides |
| ⭐ Differentiator | Meter entry validation rejecting out-of-sequence readings, with an override path | Documented failure mode: AUTOsist reviewers report same-day fuel-ups confusing the previous-odometer logic |
| ⭐ Differentiator | Snooze, so a legitimately deferred unit doesn't poison the overdue count | |
| 🔵 Advanced | Recall / service campaign tracking across the fleet | RTA "Campaign Management", Trimble Shop Planner |

### 2.4 Issues and defects

| Tier | Feature | Note |
|---|---|---|
| ✅ Table stakes | Issue object with priority (Critical/High/Medium/Low) and a 4-state lifecycle | |
| ✅ Table stakes | **Resolved and Closed as distinct terminal states** | Resolved-with-work vs closed-without-work. Collapsing them makes the backlog metric theatre |
| ⭐ Differentiator | Overdue triggers on **due date OR meter threshold** | "Fix within 2,000 miles" matches how a defect actually degrades |
| ⭐ Differentiator | Failed inspection items **auto-create issues** | Closes the DVIR loop required by 49 CFR 396.11 and generates the unscheduled-work event stream for free |
| ⭐ Differentiator | Time-to-resolve **and meter-delta-to-resolve** | The meter delta is "how many miles did we run this truck with a known defect" — a real risk number |

### 2.5 The shop board itself

| Tier | Feature | Note |
|---|---|---|
| ✅ Table stakes | Kanban board with status swim lanes and **drag-to-reprioritise that persists** | Tekmetric saves the drag order as a sort option — build the sort index into the row, don't rely on client-side ordering |
| ✅ Table stakes | **Tiny status vocabulary.** Tekmetric's whole WIP set is three values | Every extra status is a training cost and a dead column on the board |
| ✅ Table stakes | Quick actions on the card that advance the lifecycle in one click | "Too many clicks" is the #1 complaint against both Fullbay and Trimble TMT |
| ✅ Table stakes | Promised date/time on the card with visible aging treatment | The cheapest way to make a board self-triaging |
| ⭐ Differentiator | **Board grouping toggle**: by status / by technician / by date | One board, three mental models — admin wants status, foreman wants technician, dispatcher wants promised time. A group-by key over one query, not three screens |
| ⭐ Differentiator | **Technician board** with a "No Tech Assigned" column and assigned/complete/incomplete hours in each column header | The dispatch view and the capacity view in one |
| ⭐ Differentiator | **Line-level technician assignment** — multiple techs on one work order | A truck in a bay routinely has a PM tech and a driveability tech. Header-level-only assignment is a design mistake you cannot undo cheaply |
| ⭐ Differentiator | Colour labels **orthogonal to status** | Status answers "where is it"; labels answer "what kind is it". Two fields, not one overloaded enum |
| ⭐ Differentiator | Progress indicator (completed lines ÷ total lines) | Do **not** fake it with a status→percentage mapping |
| ⭐ Differentiator | **Hold reason** on held work: waiting parts / authorization / technician / outside vendor / tow | Aging without a hold reason is unactionable. A 20-day-old order blocked on a backordered turbo is a purchasing problem, not a shop problem |
| ⭐ Differentiator | Supervisor QA gate ("Ready for Review") before close | One status that stops half-documented orders entering history |
| ⭐ Differentiator | Quick/express work order that auto-closes | Tire swap, bulb, DEF top-off. Forcing full ceremony is how techs start avoiding the system |

### 2.6 Labor and technicians

| Tier | Feature | Note |
|---|---|---|
| ✅ Table stakes | Technician as a **first-class user**, not a free-text name | So the audit trail survives turnover |
| ✅ Table stakes | Clock on/off against a specific work order **line** | The source of every labor KPI |
| ✅ Table stakes | **Complaint / Cause / Correction** per task | The universal heavy-duty narrative format. Three text fields, near-zero cost, huge value when reading history two years later |
| ⭐ Differentiator | Direct vs indirect vs idle labor classification | Without indirect capture, technician-productivity KPIs are garbage because unbilled hours vanish |
| ⭐ Differentiator | **Kiosk mode** — one shared shop tablet, individual technician credentials | Directly compatible with our QR entry point: scan sticker → pick name → PIN → clock on |
| ⭐ Differentiator | Immutable labor transactions with **void, not delete** | Labor records become payroll evidence; you will not be allowed to hard-delete them later |
| 🔵 Advanced | Standard/estimated hours per job code vs actual clocked time | Powers technician efficiency with no financial data at all |
| 🔵 Advanced | Alert when clocked labor exceeds estimated hours | Catches the job that has silently eaten a day |

### 2.7 Admin dashboard

| Tier | Feature | Note |
|---|---|---|
| ✅ Table stakes | Fleet table with per-unit status, next-due, open-issue count | |
| ✅ Table stakes | **Snapshot KPI tiles + trailing-30-day trend, with drill-through** | A snapshot alone is noisy; a trailing average alone hides today's crisis. Both, plus click-through to the actual rows, is what makes an ops person act rather than look |
| ⭐ Differentiator | Availability / downtime / PM compliance KPIs | **The hardest thing to retrofit** — needs a status *event log*, not a status field. See [SCHEMA_AND_DATA_MODEL.md](SCHEMA_AND_DATA_MODEL.md) §6 |
| ⭐ Differentiator | Saved views / board view selector | "Where did that work order go" is a top support question |

### 2.8 Deliberately out of scope for now

| Feature | Why deferred |
|---|---|
| Parts inventory + purchase orders | Needs five tables to do correctly. Every vendor gates it to their top tier — the market agrees it's late-stage. Leave a nullable `PartId` on line items |
| Financials, invoicing, rate cards | Owner's explicit sequencing. Every financial field in Fleetio's model is an *additive column* on rows we already have — deferring costs nothing structurally |
| Telematics / fault code ingestion | High-leverage later. Heavy-duty codes are J1939 SPN+FMI+OC — three integer columns, not one string |
| Warranty claim generation | A boolean "was this under warranty" + install-date lookup gets 80% of the value first |
| Customer portal | No external customers — this is an internal fleet |
| Voice-to-text technician notes | Fullbay gates this to $258/mo tiers. Browser `SpeechRecognition` + an LLM pass covers it near-free, later |
| MCP server for AI agents | Limble ships this on Premium+ as of 2026 — leading edge. Cheap to add later *if the data model is clean*, which is the point of getting the schema right now |

## 3. Roadmap

Each step ends in something you can **see and test**. Steps 1–6 are the current focus.

### Step 1 — Repo structure and solution
Four .NET projects that build. Git initialised. Nothing runs yet.
**You can verify:** `dotnet build` succeeds.

### Step 2 — PostgreSQL in Docker
One command starts a database on your machine.
**You can verify:** connect to it and see an empty database.

### Step 3 — Schema and seed data
`Yards`, `AssetTypes`, `AssetStatuses`, `Assets` tables, created by a migration, seeded with a
realistic dump-truck and tractor fleet.
**You can verify:** query the tables and see your trucks.

### Step 4 — The API
`GET /api/units` returns the fleet as JSON, with paging.
**You can verify:** open it in a browser and see the JSON.

### Step 5 — The dashboard page
React table showing every unit with status, meters and yard.
**You can verify:** open `localhost:8890` and see your fleet.

### Step 6 — Containers
API and UI both running as containers, exactly as they will on Google Cloud.
**You can verify:** `docker compose up` and the dashboard still works.

### Step 7 — Deploy to Google Cloud
Two Cloud Run services, Neon Postgres, images in Artifact Registry.
**You can verify:** open the public URL on your phone.

### Then, in order of value

| Phase | What | Why this order |
|---|---|---|
| 8 | **Admin auth** | Must exist before real data goes in |
| 9 | **QR stickers + unit page** | The core workflow. Label generation, `/u/{token}` route, mobile-first layout |
| 10 | **Meters + issues** | The two things mechanics write most often. Unlocks "open issues" on the unit page |
| 11 | **Service tasks, reminders, history** | The "service due soon" meters. Needs meters (10) to be real |
| 12 | **Status log + availability KPIs** | Needs history to compute against. The status *log* starts in phase 9 even though charts come here |
| 13 | **Work orders + shop board kanban** | The full board. Deliberately last of the core — `ServiceEntry` already captures history, so this adds workflow, not data |
| 14 | **Roles: technician / foreman / parts / admin** | Needs work orders to have anything meaningful to gate |
| 15 | **Inspections / DVIR** | Closes the compliance loop and feeds issues automatically |

> **Why work orders come last of the core:** Fleetio itself auto-generates a service entry from a
> completed work order, which proves that adding work orders later does not invalidate any service
> history recorded before them. That's what makes this ordering safe.

## 4. Where we can beat the incumbents

Honest assessment. Four places where an in-house build has a genuine structural advantage:

1. **Native-camera QR scan.** Every incumbent makes you open their app first. A plain HTTPS URL is
   strictly better for the single most frequent interaction, and it costs us nothing.
2. **No seat licensing.** Fleetio meters custom roles (4 on Professional, 30 on Premium); UpKeep
   locks SSO and custom roles to Enterprise; Fullbay charges $188+/user. We give every mechanic,
   driver and dispatcher a login and it costs us a database row.
3. **No storage paywall.** Every vendor meters attachments. Cloud Storage costs us cents.
4. **VMRS from day one.** Only ~22% of heavy-duty shops code repairs properly. It's free to capture
   now and impossible to backfill later — and it's what makes comeback rate and top-failing-system
   analysis computable at all.

And one honest disadvantage: **we own the whole write path for inspections.** Fleetio's API is
read-only for inspection submissions, so there's no vendor precedent to copy there.

## 5. Notes and known gaps

- Pricing figures are as published at the time of research (2026-08) and change frequently. Treat
  them as directional.
- Vendor-published benchmark claims ("95% is best in class", "average fleet runs 62% PM compliance")
  are marketing, not audited. The ATRI and TMC/FleetNet figures cited in
  [SCHEMA_AND_DATA_MODEL.md](SCHEMA_AND_DATA_MODEL.md) §6 are the more defensible sources — and the
  public TMC miles-between-breakdown series stops around Q4 2021.
- The shop-board UX patterns come from light-duty leaders (Tekmetric, Shop-Ware) as much as
  heavy-duty ones, because their boards are simply better designed. The workflow translates; the
  parts catalog does not.
