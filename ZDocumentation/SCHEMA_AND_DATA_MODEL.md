# SCHEMA AND DATA MODEL

This document is the working map of myShopBoard's database design — read it before adding a table,
a column, or a status value.

It is derived from a teardown of how the industry leaders actually model this domain (Fleetio's
public OpenAPI spec, Samsara's DVIR/defect API, Limble, UpKeep, Fiix, MaintainX, Trimble TMT), plus
the US federal regulations that make some of these records legally mandatory.

---

## TL;DR — the five decisions that matter

If you remember nothing else from this document, remember these. Each one is cheap now and
extremely expensive to retrofit.

| # | Decision | Why it cannot wait |
|---|---|---|
| 1 | **Meter readings are an append-only event table**, never a `CurrentOdometer` column | A mutable column makes a fat-fingered `999999` unrecoverable and silently corrupts every service-due date on that truck forever. Every vendor that got this right (Fleetio, UpKeep, Limble) uses an event table with a **void flag** and caches the latest valid value on the asset. |
| 2 | **Every asset carries TWO meters**: odometer *and* engine hours | A dump truck idling on a job site burns engine hours while the odometer barely moves. A miles-only schedule silently under-services your dump trucks; an hours-only schedule under-services your highway tractors. Adding the second meter later touches every due-date query. |
| 3 | **Availability comes from a status-change log**, not a current-status column | "How many hours was unit 214 in the shop last month" is unanswerable from a single `Status` column. This log is the *only* source for 4 of your 6 dashboard KPIs. |
| 4 | **Status values are rows in a lookup table**, not a C# enum or Postgres enum | The shop will invent new statuses ("Waiting on Parts", "Waiting on Authorization"). An enum needs a code change and a migration each time — and you lose the behaviour flags (`IsAvailable`, `IsInShop`) that drive the KPIs. |
| 5 | **Nothing is ever hard-deleted** | 49 CFR 396.3(c) requires maintenance records for **1 year in service plus 6 months after the vehicle leaves your control**. 396.11(a)(4) requires DVIRs and repair certifications for **3 months**. Deletes are `void`/`archived_at` flags with a purge job. |

## 1. Naming and type conventions

Matching myStorage exactly (see [ARCHITECTURE.md](ARCHITECTURE.md) §1 decisions 12–13).

| Concern | Convention |
|---|---|
| Table names | PascalCase, plural, quoted in Postgres — `"Assets"`, `"MeterEntries"` |
| Column names | PascalCase — `"UnitNumber"`, `"RecordedAtUtc"` |
| Primary keys | `long` identity (`bigint GENERATED BY DEFAULT AS IDENTITY`), column name `Id` |
| Foreign keys | `<Entity>Id` — `AssetId`, `ServiceTaskId` |
| Timestamps | `DateTime` (never `DateTimeOffset`), always UTC, always `timestamp with time zone` |
| Timestamp naming | Suffix `Utc` — `CreatedAtUtc`, `CompletedAtUtc`. myStorage omits this suffix; adding it removes a whole class of timezone bug. |
| Money | **integer cents** (`long`), never `decimal` or `float`. Column suffix `Cents`. |
| Physical quantities | `decimal(18,2)` — meter values, hours |
| Rates | `decimal(18,4)` |
| Status/kind values | FK to a lookup table (see decision #4), **not** an enum |
| Booleans | Positive phrasing — `IsActive` not `IsNotActive` |
| Audit fields | `CreatedAtUtc`, `CreatedByUserId`, `UpdatedAtUtc`, `UpdatedByUserId` — set by a `SaveChanges` interceptor, never by hand |
| Soft delete | `ArchivedAtUtc` nullable + an EF **global query filter** |

> **User IDs are `string`, not `long`.** ASP.NET Core Identity uses a `string` primary key. Every FK
> to a user is `[MaxLength(450)] string`. This matches myStorage and is required for the two apps'
> identities to ever merge.

## 2. Entity map

```
                        ┌──────────┐
                        │   Yard   │  (your shops/terminals — decision #6 in ARCHITECTURE.md)
                        └────┬─────┘
                             │
   ┌─────────────┐      ┌────▼──────┐      ┌──────────────┐
   │  AssetType  ├─────>│           │<─────┤ AssetStatus  │ (lookup table + behaviour flags)
   └─────────────┘      │   Asset   │      └──────┬───────┘
                        │  (a unit) │             │
   ┌─────────────┐      │           │      ┌──────▼─────────────┐
   │ AssetGroup  ├─────>│           │      │ AssetStatusChange  │ ← ALL availability KPIs
   └─────────────┘      └─┬───┬───┬─┘      └────────────────────┘
                          │   │   │
      ┌───────────────────┘   │   └────────────────────┐
      │                       │                        │
┌─────▼────────┐    ┌─────────▼─────────┐    ┌─────────▼────────┐
│ MeterEntry   │    │ ServiceReminder   │    │      Issue       │
│ (append-only)│    │ (the PM schedule) │    │ (a defect)       │
└──────────────┘    └─────────┬─────────┘    └─────────┬────────┘
                              │                        │
                        ┌─────▼───────┐                │
                        │ ServiceTask │                │ resolved by
                        │  (catalog)  │                │
                        └─────────────┘                │
                                                       │
                   ┌───────────────────┐               │
                   │   ServiceEntry    │<──────────────┘
                   │ (work performed)  │
                   └─────────┬─────────┘
                             │
                   ┌─────────▼──────────────┐
                   │ ServiceEntryLineItem   │  (carries VMRS codes)
                   └────────────────────────┘

  Cross-cutting, attached polymorphically:  Attachment · Comment · AuditLog
```

**The three-way split is the core CMMS pattern** and it trips everyone up the first time:

- **`ServiceTask`** — the *catalog*. "Engine Oil & Filter Change" exists once for the whole company.
- **`ServiceReminder`** — the *schedule*. "Unit 214 does Engine Oil every 15,000 mi or 250 hrs or 6 months."
- **`ServiceEntry`** — the *event*. "On 2026-07-14 at 182,431 mi, Dave changed the oil on unit 214."

## 4. Phase 2+ tables (designed now, built later)

These are specified here so Phase 1's tables have the right shape to receive them. **Do not build
them yet.**

### `AssetStatusChanges` — the KPI engine (Phase 3, before any KPI work)

| Column | Type |
|---|---|
| `Id` | `long` PK |
| `AssetId` | `long` FK |
| `FromStatusId` | `long` FK NULL (null = initial) |
| `ToStatusId` | `long` FK |
| `ChangedAtUtc` | `datetime` |
| `ChangedByUserId` | `varchar(450)` |
| `Reason` | `varchar(500)` NULL |

Availability is **derived** from this with a window function over `lag(ChangedAtUtc)`. Never store a
computed availability number.

### `MeterEntries` — append-only (Phase 3)

| Column | Type | Notes |
|---|---|---|
| `Id` | `long` PK | |
| `AssetId` | `long` FK | |
| `MeterType` | `varchar(10)` | `primary` / `secondary` |
| `Value` | `decimal(18,2)` | |
| `RecordedAtUtc` | `datetime` | |
| `Source` | `varchar(20)` | `manual` / `inspection` / `service` / `telematics` |
| `SourceRecordId` | `long` NULL | back-pointer to what created it |
| `IsVoid` | `bool` | **flag, never delete** |
| `VoidReason` | `varchar(200)` NULL | |
| `CreatedByUserId` | `varchar(450)` | |

**Index:** `(AssetId, MeterType, RecordedAtUtc DESC) WHERE IsVoid = false`.

Do **not** put a unique constraint on `(AssetId, MeterType, RecordedAtUtc)` — two readings can
legitimately share a timestamp.

### `ServiceTasks` — the catalog (Phase 3)

`Id`, `Name`, `Description`, `DefaultVmrsSystemCode`, `DefaultVmrsAssemblyCode`,
`DefaultVmrsComponentCode`, `IsActive`.

Seeded with the PM tiers the heavy-truck industry actually uses:

| Task | Typical interval |
|---|---|
| PM-A — basic safety / oil | 5,000–15,000 mi **or** 250 engine hours |
| PM-B — intermediate, filters / drivetrain | 25,000–30,000 mi |
| PM-C — comprehensive, transmission / differential / alignment | 50,000–60,000 mi |
| PM-D — major + DOT inspection | 100,000 mi **or** annually |
| DOT Annual Inspection (49 CFR 396.17) | 12 months |

### `ServiceReminders` — the schedule (Phase 3)

This table is why the "service due soon" widget on the truck page works. It carries **three parallel
intervals** and each has its own due-soon threshold.

| Column group | Columns |
|---|---|
| Identity | `Id`, `AssetId`, `ServiceTaskId`, `ProgramId` NULL |
| Recurring intervals | `MeterInterval`, `SecondaryMeterInterval`, `TimeInterval`, `TimeFrequency` (`days`/`weeks`/`months`/`years`) |
| First-service override | `StartingMeterInterval`, `StartingSecondaryMeterInterval`, `StartingTimeInterval`, `StartingTimeFrequency` |
| Computed next-due | `NextDueMeterValue`, `NextDueSecondaryMeterValue`, `NextDueAtUtc` |
| Due-soon thresholds | `DueSoonMeterThreshold`, `DueSoonSecondaryMeterThreshold`, `DueSoonTimeThresholdInterval`, `DueSoonTimeThresholdFrequency` |
| State | `LastServiceEntryId`, `SnoozedUntilUtc` |

**Rules copied from Fleetio's documented behaviour:**

1. At least one of meter / secondary-meter / time must be set. All three may be set at once, and the
   reminder fires on **whichever comes due first**.
2. On completion: `NextDueMeter = (meter reading at the completed service) + MeterInterval`.
   **Not** `previous due + interval` — otherwise a late PM permanently shifts the schedule.
3. If the completing service has no valid meter reading, fall back to **the last valid meter entry**.
   Skip this and one voided reading makes a truck look permanently overdue.
4. Status is derived, not stored: `OK` / `Due Soon` / `Overdue` / `Snoozed`.

**Index:** `(NextDueAtUtc)` and `(AssetId, NextDueMeterValue)` for the fleet-wide due-soon query.

### `Issues` — defects (Phase 4)

`Id`, `AssetId`, `Summary`, `Description`, `ReportedAtUtc`, `ReportedByUserId`, `Priority`,
`StatusId`, `MeterEntryId` NULL, `DueDate` NULL, **`DueMeterValue` NULL**, `AssignedToUserId` NULL,
`ResolvedAtUtc`, `ResolvedByUserId`, `ResolvedServiceEntryId` NULL.

> **`DueMeterValue` is what makes an open issue meaningful on a truck page.** "Fix within 30 days"
> is weak; "fix within 2,000 miles" matches how a defect actually degrades. Both triggers, either
> can fire.

`Resolved` and `Closed` are **distinct terminal states** — resolved-with-work vs closed-without-work.
Collapsing them makes the backlog metric dishonest.

### `ServiceEntries` + `ServiceEntryLineItems` (Phase 4)

The record of work performed. Header carries `AssetId`, `StartedAtUtc`, `CompletedAtUtc`,
`MeterEntryId`, `SecondaryMeterEntryId`, `VendorId` NULL, `Reference`, `GeneralNotes`.

Line items carry `ServiceTaskId`, `Notes`, `Position`, and **four VMRS columns**:
`VmrsReasonForRepair`, `VmrsSystemCode`, `VmrsAssemblyCode`, `VmrsComponentCode`.

> **On VMRS:** it's the trucking industry's standard parts/repair taxonomy from the ATA's Technology
> & Maintenance Council. A code like `013-001-002` means system 013 (braking) → assembly → component.
> Capturing it is what makes "which system fails most" and "did this repair come back" computable —
> free-text "fixed brake issue" does not join to "brakes still dragging". Only ~22% of heavy-duty
> shops do this, so it's a genuine differentiator.
>
> **Licensing caveat:** the code *tables* are ATA TMC licensed content. Designing the four columns is
> free; redistributing the published code list is not. We seed a small internal subset and license
> later if it matters.

### `WorkOrders` (Phase 5 — deliberately deferred)

Fleetio itself auto-generates a `ServiceEntry` from a completed `WorkOrder`, which proves adding
work orders later does **not** invalidate service history recorded in Phase 4.

When it lands: `WorkOrders` + `WorkOrderStatuses` (lookup with an `IsCompletedState` flag that locks
the record) + `WorkOrderLineItems` (polymorphic `Kind` ∈ `task`/`labor`/`part`) + a
**`WorkOrderIssues` join table** — one work order resolves *many* issues, so a scalar FK on `Issue`
would force a rewrite.

Also needs `HoldReason` ∈ waiting-parts / waiting-authorization / waiting-technician /
waiting-outside-vendor / waiting-tow. Work-order aging without a hold reason is an unactionable
number: a 20-day-old order blocked on a backordered turbo is a *purchasing* problem, not a shop
problem, and the dashboard should say which.

### Cross-cutting (Phase 4)

`Attachments` (`OwnerType`, `OwnerId`, `GcsObjectName`, `ContentType`, `Bytes`, `UploadedByUserId`),
`Comments` (same polymorphic shape), `AuditLog` (`ActorUserId`, `EntityType`, `EntityId`, `Action`,
`Diff` JSONB, `AtUtc`).

Building these generically once avoids N copies of a notes table.

## 5. QR sticker design

| Aspect | Decision | Source |
|---|---|---|
| URL shape | `https://<host>/u/{QrToken}` | |
| Token | **128-bit CSPRNG**, base62, stored in `Asset.QrToken` — *not* the numeric `Id`, *not* the VIN | W3C TAG Capability URLs: "a random value with sufficiently high entropy (120 bits or more)"; sequential integers explicitly discouraged |
| Not UUIDv7/ULID | Those leak creation time **and creation order** of every unit in the fleet | RFC 9562 §5.7 |
| Access | **Login required** (your decision #8). The random token is defence in depth, never the control | OWASP IDOR Cheat Sheet: "even with complex identifiers, access control checks are essential" |
| Scanner | **The phone's native camera app** — no in-app scanner needed | See below |
| Error correction | **Level H** (recovers 30% damage) | Mud, scratches and paint overspray behave exactly like the damage EC is designed for |
| Physical size | **4–5 cm minimum**, quiet zone ≥ 4 modules | Max scan distance ≈ 10× code width; a mechanic scans at arm's length (~30 cm) |
| Label stock | **Anodized aluminium** (rated 385–400°F) near hot zones | Destructible vinyl is rated 170°F — rules it out near the exhaust stack, turbo, DPF, or engine bay |
| Placement | Driver-door jamb **plus a second location**, reachable without climbing, above the tire spray line | So one destroyed sticker doesn't orphan the unit |
| Second factor | Print the **unit number in human-readable text** next to the QR | Every truck already carries legally-required legible markings under 49 CFR 390.21; matching that style gives a free "am I looking at the right truck" check |

> **Why no in-app camera scanner:** the browser `BarcodeDetector` API is at ~76% support and is
> **unsupported in Safari on iOS entirely**, plus there is a long-standing WebKit bug class where
> `getUserMedia` fails in home-screen PWAs. The native camera app opens the URL directly, works on
> every phone, needs no camera permission from our origin, and dodges all of it. Build a web scanner
> only later, for scan-from-inside-a-form flows.

## 6. The KPI contract

The dashboard's six MVP KPIs and exactly what must be logged for each to be computable. **Never
store a computed KPI** — derive them.

| KPI | Formula | Depends on |
|---|---|---|
| **Fleet availability %** | (Σ unit-hours in an `IsAvailable` status ÷ Σ unit-hours **scheduled to work**) × 100 | `AssetStatusChanges` + a scheduled-operating calendar |
| **Downtime hours** | Σ (end − start) over out-of-service intervals, split planned vs unplanned | `AssetStatusChanges` + `IsPlannedDowntime` flag |
| **PM compliance %** | (PMs completed within **±10% of interval** ÷ PMs scheduled) × 100 | `ServiceReminders` + `ServiceEntries` |
| **Work order / issue aging** | Now − `ReportedAtUtc`, bucketed, grouped by hold reason | `Issues` (+ `WorkOrders` later) |
| **Miles between breakdowns** | Total fleet miles ÷ unscheduled road repairs | `MeterEntries` + an `is_failure` distinction |
| **Mean time to restore** | Σ (released − out-of-service) ÷ unplanned events | `AssetStatusChanges` |

### Gotchas that make these numbers honest

1. **The availability denominator is scheduled operating days, not calendar days.** Dump fleets park
   units seasonally and between projects. Counting parked units as "down" collapses availability to
   a meaningless number and the KPI gets ignored within a month. This is what
   `AssetStatus.ExcludeFromAvailability` is for.

2. **Measure out-of-service → released-to-dispatch, not wrench-start → wrench-finish.** The gap
   between them is waiting-on-parts and waiting-on-authorization — usually the largest single bucket
   and the only one management can actually fix.

3. **The PM ±10% rule.** A PM counts as on-time only if completed within 10% of its interval:
   a 90-day interval → ±9 days; 15,000 mi → ±1,500 mi; 250 hours → ±25 hours. Without this,
   late completions silently inflate the score.

4. **A meter-based reminder never fires if nobody logs the meter.** PM compliance then reads a
   perfect 100% on exactly the units nobody is scanning. Surface "meter not read in N days" as its
   own alert.

5. **Show "insufficient data" instead of a number.** A 20–100 unit fleet generates too few failures
   for monthly MTBF/MTTR to be stable. "2.1 h MTTR" computed from three events is worse than
   showing nothing. Use a 90-day minimum window.

6. **Benchmarks for context** (cite these as external, not as your targets): 95%+ availability is a
   well-managed fleet, below 90% signals a serious problem. Industry average is ~38,249 miles
   between breakdowns (ATRI 2024). PM compliance ≥90% is the common target. Unplanned downtime
   costs $1,000–$2,000+/day for heavy-duty operations.

## 7. Regulatory records this schema must satisfy

Not optional — these are federal requirements for a motor carrier, and the schema above already
covers them. Modelling them properly means the Shop Board **doubles as your DOT audit file**.

| Regulation | Requirement | Satisfied by |
|---|---|---|
| **49 CFR 396.3(b)(1)** | Identify the vehicle: company number, make, serial number, year | `Assets.UnitNumber`, `Make`, `Vin`, `Year` |
| **49 CFR 396.3(b)(2)** | "A means to indicate the nature and due date of the various inspection and maintenance operations to be performed" | `ServiceReminders` — this clause *is* the service-reminder table |
| **49 CFR 396.3(b)(3)** | "A record of inspection, repairs, and maintenance indicating their date and nature" | `ServiceEntries` + `ServiceEntryLineItems` |
| **49 CFR 396.3(c)** | Retain **1 year** while in service **+ 6 months** after the vehicle leaves your control | `ArchivedAtUtc` soft delete + an 18-month purge job. **This is why nothing is hard-deleted.** |
| **49 CFR 396.11** | Driver Vehicle Inspection Reports covering 11 named items; driver signs, carrier certifies repair, driver reviews | `InspectionForms` / `InspectionSubmissions` (Phase 5) with **three signature slots** |
| **49 CFR 396.11(a)(4)** | Retain DVIR + repair certification + driver review certification for **3 months** | same |
| **49 CFR 396.17** | Annual periodic inspection | `ServiceTasks` "DOT Annual Inspection" + `AssetTypes.RequiresDotAnnual` |

The 11 DVIR items to seed as the default inspection form: service brakes (including trailer brake
connections), parking brake, steering mechanism, lighting devices and reflectors, tires, horn,
windshield wipers, rear vision mirrors, coupling devices, wheels and rims, emergency equipment.

## 8. Dump-truck specifics

Things a vocational fleet needs that a highway-tractor-only model would miss:

- **Engine hours matter as much as miles.** Covered by the dual-meter design. A rule of thumb used
  in the industry (vendor guidance, not a standard): 1 engine hour ≈ 25–33 miles of diesel wear —
  which is why "5,000 mi **or** 250 hours, whichever first" is the standard vocational PM trigger.
- **PTO hours** may eventually warrant a third meter. The `MeterType` column is a string, not a
  two-valued enum, specifically so this doesn't need a migration.
- **Hydraulic hoist, tailgate, body/bed, tarp system** are components a tractor doesn't have. They
  are `ServiceTask` rows and VMRS component codes, not schema changes.
- **Tandem/tri-axle tire rotation** — a `ServiceTask`, deferred until tire tracking is real.

## 9. Invariants and gotchas (read before changing anything)

1. **Never hard-delete a meter entry, service record, or inspection.** Use `IsVoid` / `ArchivedAtUtc`.
   Federal retention requires it, and voiding must leave the parent record intact — Fleetio's exact
   semantics: "the Inspection, Fuel Entry, and Service Entry data will remain intact."

2. **`CurrentPrimaryMeter` on `Assets` is a cache.** Recompute it on every meter insert or void.
   If you ever find code writing it as the source of truth, that's a bug.

3. **Don't compute availability from work-order dates.** A work order can be open while the truck is
   working, and a truck can sit down waiting on parts with no work-order activity at all. Only
   `AssetStatusChanges` is truthful.

4. **Link work orders to issues via the join table.** One completed work order resolves many issues.

5. **Store a unit on every meter value.** Never assume miles. Samsara reports odometer in *meters*;
   Fleetio uses per-vehicle mi/km/hr. Unit normalisation belongs at the integration boundary.

6. **Money is integer cents.** Every financial field in Fleetio's model is an additive column on rows
   we already have (`labor_subtotal`, `parts_subtotal`, `discount`, `tax1`, `tax2`, markups) — which
   is the proof that deferring the financials module costs nothing structurally.

7. **`QrToken` is immutable in normal operation** so printed stickers never go stale.
   `QrTokenRotatedAtUtc` is the break-glass path if a sticker is compromised.

## 10. Notes and known gaps

- **Parts inventory is deferred.** Doing it correctly needs five tables (`Part`, `PartLocation`,
  `PartLocationDetail`, `InventoryJournalEntry`, `InventoryAdjustmentReason`). Until parts *cost* is
  tracked, parts are free text on a line item.
- **Also deferred, all additive:** purchase orders, vendor payment profiles, expense entries, fuel
  entries, acquisition/lease fields, tires, axle configs.
- **Telematics ingestion is out of scope** but the schema is ready: heavy-duty fault codes are
  **J1939 SPN + FMI + OC**, three integer columns — not a single OBD-II string. Model it that way
  from the start if it's ever built.
- **Fleetio's OpenAPI is date-versioned** (`2025-05-05` current). Any field list here should be
  re-verified against the live spec before writing integration code.
- **The scheduled-operating calendar** needed for an honest availability denominator is not yet
  designed. Simplest first version: a per-asset weekly schedule plus a seasonal-parked status.
